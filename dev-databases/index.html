    Dev database backups for the sandbox¶

    Many applications don't start without their database. Operators can upload a backup of an application's development database (SQL Server, PostgreSQL or MySQL) on the admin pages, together with instructions for the AI on how to point the application at it. The next scan of the application restores the backup into a database that runs next to the application in the sandbox namespace, and sets the application's connection settings. The application's code is not changed: only the generated Kubernetes manifests are.

    On the appliance, the backup's engine must be on under Admin → Lab services. SQL Server is on by default. An app without a backup gets an empty database of its own on the lab's server instead.

    Engine Files Restored with
    SQL Server .bak made with BACKUP DATABASE ... TO DISK, compressed or not RESTORE DATABASE ... WITH MOVE
    PostgreSQL pg_dump custom format (-Fc), or a plain SQL dump (.sql, .sql.gz) pg_restore, or psql
    MySQL mysqldump or mariadb-dump output (.sql, .sql.gz) mysql

    The file's first bytes decide what it is: TAPE or MSSQLBAK (SQL Server), PGDMP (pg_dump custom format), or the dump header -- PostgreSQL database dump, -- MySQL dump or -- MariaDB dump (also inside a gzip file). A plain dump made from another database name is restored into the name you give. For PostgreSQL and MySQL, its CREATE DATABASE, USE and \connect lines are left out.

    How it works¶

    operator ──upload backup + instructions──> web UI ──> /var/lib/containerizer/devdb/<sha256>.<bak|dump|sql|sql.gz>
                                           └──> DevDatabase row (name, size, SHA-256, instructions, who)
scan worker ──reads DevDatabase──> builds <registry>/<app>/devdb:<tag> (backup inside) ──push──> registry
            └──> generated manifests: devdb Deployment + Service + NetworkPolicy, app env → devdb
    1. Upload (Admin → Dev databases, admins and operators). The file is streamed to disk, so it is never held in memory. The page checks the session, the role and the Origin header before it reads the request body. It checks the form's CSRF token, which is the first field, before it writes any of the file. The file must start with the signature of the selected engine (see above). It is stored under its SHA-256, readable only by the web UI and the scan worker, and the web UI never serves it back. The size limit is 2048 MB.
    2. Instructions. The form starts from a template. Name the setting that holds the connection string (for example ConnectionStrings:Shop), test users, and anything else the AI needs. Never put a password here. You can edit the instructions later without uploading the file again.
    3. The scan. When an application has a backup, the scan:
    4. checks the file against its SHA-256;
    5. builds an image that contains the backup, FROM mcr.microsoft.com/mssql/server:2025-latest, postgres:18-alpine or mysql:8.4 (override them with devdb: <engine>: in rules/images.yaml). SQL Server 2025 restores backups from older versions too (SQL Server 2008 and later), and upgrades the database as it restores it;
    6. pushes the image as <registry>/<app>/devdb:<tag>, also tagged sha-<first 12 of the SHA-256>.

    Each time the database pod starts, it: - restores the backup. SQL Server moves every data and log file into its data volume. PostgreSQL and MySQL restore it through the image's own /docker-entrypoint-initdb.d, while the server listens only on its local socket; - creates the user app, which owns the restored database and nothing else. On SQL Server it is a member of db_owner, not sysadmin. On PostgreSQL it owns the database, and the dump is restored as app without the dump's owners and grants. On MySQL it has all rights on that database only, and root can log in only from inside the container; - only then reports ready, because it listens on TCP only after the restore.

    Nothing is kept on a persistent volume. The database is a disposable copy, and it is restored again whenever its pod starts. 4. The application's settings. - With the LLM (Ask the LLM on the scan): the AI reads the instructions and the configuration the scan found. It answers with environment variables written as templates (only {host} {port} {database} {user} {password}). Every answer is validated, and anything that contains a literal password, a $(...) reference or an unknown placeholder is dropped. - Without the LLM (or when its answer has nothing usable): every connection string the scan found in appsettings*.json points at the database. If it found none, the scan sets ConnectionStrings__DefaultConnection.

    The password is never written into a manifest. The container gets CZ_DEVDB_PASSWORD from the Secret devdb, and the connection string refers to it with Kubernetes' $(CZ_DEVDB_PASSWORD) expansion.

    These settings replace any secret reference with the same name that the generator made for the connection string. devdb/README.md in the generated folder lists what was set, and why.

    What runs in the sandbox¶

    Object What it does
    Deployment devdb One replica, Recreate strategy. Pod Security "restricted": runs as a non-root user (SQL Server 10001, PostgreSQL 70, MySQL 999), read-only root filesystem, all capabilities dropped, no privilege escalation, RuntimeDefault seccomp, no service account token. A 4 GiB emptyDir for the data folder and small ones where the server writes its socket and temporary files. Memory: SQL Server 2 to 3 GiB, PostgreSQL 256 MiB to 1 GiB, MySQL 512 MiB to 1 GiB (fits the namespace LimitRange; the ResourceQuota counts it).
    Service devdb The engine's port (1433, 5432 or 3306), so the application connects to devdb.
    NetworkPolicy devdb Ingress on that port only from the application's own pods (app.kubernetes.io/part-of); egress to DNS only.
    Password + ExternalSecret devdb, devdb-admin External Secrets Operator's Password generator creates the app and admin (sa, postgres or root) passwords in the cluster, once (refreshInterval: "0"). They never leave the cluster and need nothing in the secret store (external-secrets.md).

    Two details of the SQL Server image:

    • setcap -r /opt/mssql/bin/sqlservr. The SQL Server binary carries the file capability cap_net_bind_service. Linux refuses to start a binary like that in a container that drops all capabilities ("Operation not permitted"). The server listens on 1433, so it doesn't need the capability, and the image removes it instead of adding the capability back to the pod.
    • MSSQL_PID=Developer. SQL Server Developer edition is free for development and test use, and not licensed for production. These databases only run in the sandbox.

    Browse and fix the data¶

    On the appliance, Admin → Dev databases also opens the databases the applications have in the sandbox, to look at and fix their data while you debug them: a restored dev database (above), or the application's own database on a lab service's shared SQL Server, PostgreSQL or MySQL. Only administrators and operators see the page (product owners and viewers do not, not even the link).

    • Which database. The list at the top names every application with a database in the sandbox. On an application's page, pick the database and the namespace: the application's own (also while a Make it A patch runs there in place: it uses the application's lab database), the latest first. MongoDB, Redis and the other lab services are not browsed here.
    • Tables. The tables and views, with their approximate row counts.
    • Rows. 50 a page, sorted by any column (the primary key by default), filtered on one column (equals, contains, is NULL, is not NULL). Values are shown as text: binary columns as hex, NULL as NULL.
    • Edit. Change a row, add one or delete one, always picked out by its primary key. Only the values you change are written; tick NULL for no value, and default on a new row to leave a column to the database (identity, auto-increment and columns with a default start ticked). Computed columns, rowversion and binary columns are not written here. A table without a primary key, or with a binary one, and a view are read-only, and the page says why.
    • SQL. Run one statement (on SQL Server one batch, without GO): the result table (at most 500 rows), the number of rows affected, or the database's error. A SQL Server statement whose result cannot be captured as a table (temporary tables, several result sets) shows sqlcmd's text output instead.
    • Delete the database, after typing its name:
      • a lab-service database is dropped (its open connections closed first) and the lab agent creates it again straight away, empty, with the same login and password; then the application's Deployments restart, so an application that creates its own tables (Entity Framework EnsureCreated, migrations, seed data) fills it again;
      • a restored dev database restarts. It keeps its data in its pod only, so it is restored again from the uploaded backup, which takes as long as the first restore. To stop restoring the backup, remove the backup instead.

    How a statement reaches the database¶

    web UI (cz-web) --requests/<id>.json--> system agent (root) --kubectl exec -i--> the server's own client
        ^                                    |                                   (psql, mysql, sqlcmd)
        └──────── answers/<id>.json ─────────┘                                    as the application's login

    The web UI has no access to the cluster. It hands each step to the system agent as a request carrying the signed-in user, the application, the namespace and the statements, and waits up to 45 seconds for the answer in /run/containerizer/system/answers/<id>.json (readable by root and the web UI only); otherwise it says the appliance did not answer. The agent trusts nothing in the request:

    • the namespace must be one that the results database maps to that application, and not a system namespace;
    • lab service: the lab agent must have provisioned that namespace's database. The login, password and database come from the secret store (containerizer-secrets/<ns>--cz-lab-<service>), and the agent checks them against the names it derives itself;
    • restored dev database: the ready devdb pod in that namespace; its engine and database name come from the pod, the password from the namespace's devdb Secret, the login is app.

    The statement then runs through the engine's own client inside the server's container, as the application's own login, in its own database: whatever SQL a request holds, it can only do what the application itself can do there. The password is the first line of the client's standard input, read by a fixed script into the client's environment: it is never on a command line, in a request or answer file, or sent to the web UI. Nothing in a statement reaches the client's own command language: psql -c (no backslash commands), mysql --binary-mode (no client commands, no local files), and on SQL Server the statement travels hex-encoded into sp_executesql (no : commands, no $(variables)). Values typed into the row editor are quoted for the engine (SQL Server N'…', PostgreSQL '…'/E'…', MySQL hex literals), never pasted in raw. Each statement stops after 15 seconds; an answer holds at most 500 rows and 1 MB.

    Deleting a lab-service database runs DROP DATABASE as the shared server's admin (from its own environment, as provisioning does) on the database name the agent derives itself; the typed name must match it.

    What the change history records¶

    Every change, before it runs: a row changed, added or deleted, a SQL statement (even a SELECT), a database deleted. It is recorded with who, when, the application, the namespace, the engine and the statement with its values (these are lab databases), in DatabaseEdit and the change history (Change history → Sandbox databases); the outcome (rows affected or the error) follows on the application's database page. If it cannot be recorded (a results database older than schema 38: run containerizer db init), it does not run. Looking at tables and rows is not recorded, unless the access log is on (CONTAINERIZER_VIEW_AUDIT): then each page is logged like other results pages.

    Setting it up¶

    Nothing to set up: the appliance keeps the backups on its data partition in /var/lib/containerizer/devdb, where the web UI writes them and the scan worker reads them. To allow larger uploads than 2048 MB, set CONTAINERIZER_DEV_DB_MAX_MB in /etc/containerizer/web.env and restart the web UI.

    Security notes¶

    • The backup is data. It is stored on the web UI's volume and in the registry, inside the devdb image. Use backups with test data only. Treat the registry repository <registry>/<app>/devdb like the database itself, and restrict who can pull it.
    • What the audit log records. Uploads, instruction edits and removals go to the change history (AuditLog, table DevDatabase): engine, database name, file name, size, SHA-256 and a SHA-256 of the instructions, with who made the change and in which role. The instructions themselves stay only in DevDatabase.Prompt.
    • No security gate on this image. The security gate does not scan the database image. Its base is the engine's official image, which you can pin and update through rules/images.yaml.
    • Removing a backup deletes the stored file once no application refers to it. The next scan deploys the application without the database.
