    Bug reports¶

    Sometimes a build or a run fails in the scan's verification because of Containerizer itself, not because of the application: a generated Dockerfile that cannot work, a setting the tool misread, a docker command it put together wrongly. Administrators can flag such a case where they see it and later export every flagged case as one JSON file for whoever maintains Containerizer, with the names you choose replaced.

    Nothing is sent anywhere: the export is a file you download and pass on yourself.

    Flag a failed build or run¶

    On an application's page, a component whose build or run failed has Flag as a Containerizer bug at the end of its Build and run block, with room for a short note on why it looks like the tool's fault.

    The case is copied at that moment, because the next scan of the application replaces the component's logs:

    • the component's facts (name, project path, role, target framework, verdict) and the application's rating and commit;
    • the verification result and its excerpt;
    • every attempt's Dockerfile, docker build command and log (up to 300,000 characters each: its start and its end);
    • the component's findings (rule, severity, title, evidence).

    The application's source code is not copied. Secrets are masked in the logs when the scan stores them. A component has one open report: flagging it again replaces the copy, and Remove the flag deletes it (a report that has tries is closed and kept instead, see below).

    Bug reports¶

    Admin → Bug reports lists the flagged cases with their notes.

    • Views. The page opens on the Open reports. Resolved and closed shows the ones that are dealt with, and All shows everything; each view says how many it has.
    • Resolved marks a report as fixed, Close puts one aside that will not be fixed or was not a bug after all, and Reopen brings either back. Both leave the Open view, and neither removes anything: a resolved or closed report keeps its case and its tries.
    • Resolved automatically. An open report is marked resolved by itself, the next time this page is opened, when all three hold: one of its tries got five stars, the application's latest scan rates it A, and the latest sandbox check found the component deployed and healthy. The status then says automatically: .... A report a person has set a status on, a reopened one included, is left alone.
    • Labels. Give a report labels (comma-separated, such as nuget, windows path) to keep similar cases together. The labels of the view are listed above the table with their counts; click one to see only its reports, in any view. Labels are free text, up to eight a report.
    • JSON exports one report alone, and Remove deletes a report that has no tries.

    Working through B-rated applications¶

    A rating of B means targeted code changes: the application should become A, or there should be a recorded reason why it cannot. The aim is that no application stays B without a decision. Nothing here happens by itself: it is the order in which an administrator works through them.

    1. Make it A (Refactoring patches). Most B applications end here.
    2. Try again with your own words. When the patch does not verify, flag the failed component and use Let the LLM try below with what you think is wrong, allowing code changes when the build plan is not enough. Go on from the best try, not necessarily the latest.
    3. Flag what looks like the tool's fault and export it, so Containerizer gets fixed. After the fix, scan the application again.
    4. When none of that makes it A, decide which case it is, label the report with it, and act:
    Case What to do
    Containerizer is still wrong Keep the report open for the maintainers (label it, for example tool)
    The tries showed a real obstacle in the code: a Windows-only API or library, a component that cannot move Propose a rule for it (Self-learning loop). Once a person approves it, the application is rated by that rule: C when part of it must stay on Windows and the rest can move, D when it needs a port. Then mark the report resolved
    It only needs work no LLM managed Hand the best try's patch (Download .patch) to a developer, label the report (for example developer), and close it
    • Do not change a rating because attempts failed. A rating says what the code needs, not how well the LLM or the tool did; it changes only through a rule a person approved. An application that cannot be made A leaves B by getting the rule that says why.
    • Persistent storage is not a reason for B. A component that keeps its own data rates A when it otherwise runs with configuration only: it is shown as Stateful and deployed with a persistent volume and one replica (Application data on persistent volumes). An application that is B only because of its data is a case to flag.

    Let the LLM try¶

    Often you already have an idea of what would fix the case. Write it under the report in Let the LLM try, in your own words (build on the full image and add libgdiplus), choose whether the LLM may change code, and Containerizer tests the idea for you:

    1. The LLM queue (a job of the kind Bug report try; it needs no approval unless you tick that kind in the queue's settings, since an administrator asked for it) takes the application's source at the flagged commit from the scan worker's clone.
    2. It builds and runs the component as it is, with the version installed now. If that works, the result is Already fixed and the LLM is not asked.
    3. It asks the LLM for a change that follows your words (below).
    4. It builds and runs the component again with that change, and compares.

    What the LLM may change¶

    • The build plan, always: the base image, OS packages, environment variables, writable folders, build arguments, files removed in the build, the runtime line.
    • The application's code, up to the number of lines you choose: 25, 50 (the default), 100, 200, 500 or 1,000, or No code changes. The LLM first names the files it needs to read (from the application's file list: up to three, or six when it may change more than 100 lines), then gives edits of those files; together they may change at most the lines you allowed. A larger allowance means a longer answer from the LLM, and with a slow self-hosted LLM a longer wait. Edits that change more, that do not match the file, or that remove what the application does are refused; the LLM gets one more chance, then the try goes on without a code change.

    A try makes at most three LLM calls and two builds, so it cannot run for long. The scan's own Dockerfile text is not edited directly: it follows from the plan.

    Every try is kept, and any of them can be continued¶

    Nothing of a try is thrown away: your words, the LLM's diagnosis, its plan change, the code change as a diff (with Download .patch) and the result stay with the report, and all of it goes into the export. A report that has tries cannot be removed, only closed; flagging the component again after a new scan closes the old report and keeps it.

    Continue from this try under any finished try starts the next one from that try's changes (its plan change and its code change), not from the flagged commit and not necessarily from the latest try: when the third idea made it worse, go on from the second. The page shows each try under the one it continues. A continued try takes its parent's result as its starting point, so it builds once.

    The rating¶

    Each try has a result, compared with where it started, and stars for how far the build and run got:

    Stars The build and run with the change
    ★☆☆☆☆ the build fails
    ★★☆☆☆ it builds, the run fails
    ★★★☆☆ it builds and runs into a known finding
    ★★★★☆ it runs, and stops only at missing external services
    ★★★★★ it builds and runs
    Result Meaning
    Helped It builds and runs with the change
    Got further It still fails, but later than before (more stars)
    Did not help It fails as before
    Worse It gets less far than before
    Already fixed It builds and runs with this version without any change
    Nothing to try The LLM found no change that does what you wrote (its reasoning is shown)
    Not tried The source at the flagged commit is gone, the component is no longer built in Linux, Docker is away, or the parent's code change no longer applies

    Best so far marks the try to go on from: the most stars, then the smallest change, then the earliest.

    A try changes nothing for the application itself: its next scan builds it as before, and the repository is never written to. What a try found is feedback for whoever fixes Containerizer, and a patch you can apply yourself.

    The try needs an LLM (Admin → Source control & LLM) and an organization scan on this machine that still has the commit; scan and flag the application again when it has moved on.

    System prompts¶

    A system prompt is what Containerizer tells the LLM about its role. A try asks the LLM two kinds of question, each under its own system prompt, and System prompts of this try in the try's form shows both, ready to edit:

    Prompt Used in the try for The same built-in text is used elsewhere for
    The plan change What fails, and which build-plan change follows your words Component reviews where the rules are unsure, and the diagnosis of a failed build or run
    The code change The edits of the files the LLM read Every code change of a refactoring order

    • A changed text is used for that try alone. Scans, refactoring orders and other tries keep the built-in texts; nothing on the appliance changes. A text you leave as it is stays the built-in one.
    • Continue from this try carries a try's replaced prompts into the next form, so a wording that worked stays until you change it back.
    • The question itself (the evidence, the files, your words) and the form of the answer are not part of a system prompt: an answer must still be the JSON its question asks for, so keep that instruction when you rewrite one.
    • A try shows which prompts it replaced, and the export carries them with the try, next to its result and its rating, together with the built-in texts of that version (builtin_system_prompts). That is how better wordings are found: the maintainers compare what a replaced prompt achieved across reports, and a wording that clearly works better becomes the built-in text of a later version of Containerizer.

    Version 0.54.7 let an administrator replace system prompts for the whole appliance. That is gone: a prompt replaced there is no longer used after the update, and the built-in texts apply again.

    Anonymization keywords¶

    Give the words the export must not carry, one per line: company, product, project, host and people's names.

    • Each keyword is replaced everywhere in the export (logs, paths, Dockerfiles, application and component names, your notes) by a random word such as maple-3f9a.
    • The same keyword gets the same word within one file, whatever its case, so the case stays readable: a feed host is still the same host in every line.
    • Every export draws new words, and the mapping is neither in the file nor kept.
    • Longer keywords are replaced first, so build01.contoso.local goes as a whole before contoso.
    • Application and component names are replaced only when they are listed.

    Open the file before you send it: a name that is not listed stays.
