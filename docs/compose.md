# Docker Compose (no Kubernetes)

Not every team that moves its first applications into containers runs Kubernetes. Next to
`kustomization.yaml`, each generated application folder also has a `compose.yaml`. You can run it on one Docker
or Podman host, on a PaaS that accepts Compose, or on a developer's machine. It is made from the same hardened
pod specs as the components' `k8s.yaml`. The security baseline and each component's hardening exceptions
(`rules/60-security.yaml`) carry over wherever Compose has an equivalent. The application's code is not
changed: everything is configuration around the same image.

```text
<app>/
  compose.yaml               # one service per component, the lab dependencies under the "lab" profile
  .env.example               # BIND_ADDRESS, host ports, LAB_PASSWORD: copy to .env
  .gitignore                 # keeps .env, */secrets.env and */secrets/ out of Git
  <component>/
    Dockerfile               # the same Dockerfile the build pipeline uses
    secrets.env.example      # the component's secret settings (keys only): copy to secrets.env
    k8s.yaml
```

## Running it

```sh
cd <app>
cp .env.example .env                                   # adjust ports / bind address
cp <component>/secrets.env.example <component>/secrets.env   # fill in the values
docker compose up -d --build
```

`containerizer generate` writes a `build:` section. It uses the application's folder as the build context
(a relative path from the output folder) and the generated Dockerfile, so `--build` builds the same image as
the pipeline. Applications generated by an organization scan have no `build:`. Their `image:` is the one the
[build pipeline](build-pipelines.md) pushes, so `docker compose pull && docker compose up -d` runs them.

Behind a TLS-inspecting proxy, give the Dockerfile's optional build secret `ca` your proxy's CA bundle with a
`compose.override.yaml`. Compose reads that file automatically:

```yaml
services:
  web:
    build:
      secrets: [ca]
secrets:
  ca:
    file: ./ca.crt
```

## What carries over

| Kubernetes (k8s.yaml) | compose.yaml |
| --- | --- |
| `runAsUser` / `runAsGroup` | `user: "<uid>:<gid>"` |
| `readOnlyRootFilesystem: true` | `read_only: true` |
| `capabilities.drop: [ALL]`, `add` (exceptions) | `cap_drop: [ALL]`, `cap_add` |
| `allowPrivilegeEscalation: false` | `security_opt: [no-new-privileges:true]` |
| seccomp / AppArmor `RuntimeDefault` | Docker's default profiles (nothing to set; the lint refuses `unconfined`) |
| `emptyDir` with `sizeLimit` | `tmpfs: ["/path:size=…,mode=1777"]` |
| `PersistentVolumeClaim` | named volume |
| ASP.NET Core Data Protection key Secret | named volume `<component>-dataprotection`: one host, one replica, the app keeps the key ring it makes |
| other Secret volumes (key files under `/secrets`) | read-only bind of `<component>/secrets/<volume>/` |
| `secretKeyRef` environment (the ExternalSecret's keys) | `env_file: <component>/secrets.env` (optional; never values in `compose.yaml`) |
| memory request / limit, CPU limit | `mem_reservation` / `mem_limit` / `cpus`; plus `pids_limit` |
| probes | `healthcheck`, when the image has a program to run it (below) |
| Service of a web component | `ports` on `${BIND_ADDRESS:-127.0.0.1}` |
| NetworkPolicy egress `none` | only on the `internal` network (no route out) |
| CronJob | a service under the `jobs` profile: `docker compose run --rm <job>` from cron or a systemd timer; `x-containerizer-schedule` keeps the placeholder schedule |

**Ports.** Only web components are published. By default they listen on loopback only, so nothing is reachable
from the network until you put a TLS reverse proxy in front or set `BIND_ADDRESS=0.0.0.0` in `.env`. Each
component's host port is `<COMPONENT>_PORT` in `.env`, starting from 8080.

**Networks.** Every service is on `internal`, a network with no route out. A component is also on `edge`, a
normal bridge network, when its NetworkPolicy allows egress or it publishes a port. Docker can only publish
ports from a network that has a route out. Compose has no per-destination egress rules: use the host's
firewall for the destinations in `connectivity.yaml`.

**Healthchecks.** Docker runs a healthcheck *inside* the container. Chiseled and distroless .NET images have no
shell and no HTTP client. So a component on those images gets no `healthcheck`, and its probe is kept as
`x-containerizer-probe` for a reverse proxy or an orchestrator that checks from outside. Images that can run a
check (nginx-unprivileged, Node.js, Python) get one. The table is data in `rules/compose.yaml`.

## Lab dependencies (local runs)

When a component needs SQL Server, PostgreSQL, MySQL, Redis, MongoDB, RabbitMQ, Kafka, Azure Blob (Azurite) or
S3 (the same detection as the appliance's [lab services](lab-services.md)), `compose.yaml` includes that
service under the `lab` profile:

```sh
echo 'LAB_PASSWORD=<a strong password>' >> .env       # SQL Server: 8+ characters, upper, lower and digits
docker compose --profile lab up -d
```

These are for development and test only (SQL Server is the Developer edition). They run with their images' own
users and `no-new-privileges`, only on the `internal` network, and they are not gated. The component's
`secrets.env.example` shows, as a comment, the connection string that points at the lab service. Copy it into
`secrets.env` and replace `<LAB_PASSWORD>` with your password. SFTP has no Compose definition. The images and
settings are in `rules/compose.yaml`.

## Gate

`containerizer gate` lints each component's services in `compose.yaml` with the same checks and severities
as the manifests (`rules/60-security.yaml`). It refuses:

- `privileged` and mapped devices
- host namespaces (`network_mode`, `pid`, `ipc`, `uts`, `userns_mode: host`)
- a missing `cap_drop: [ALL]`, and added capabilities beyond `NET_BIND_SERVICE`
- a missing `no-new-privileges`
- `seccomp` / `apparmor` set to `unconfined`
- running as root, and a writable root file system
- a missing memory limit
- bind mounts of host paths, or of the Docker or Podman socket
- secret-named environment variables with literal values (`${VAR}` interpolation, `env_file` and paths are fine)

A component's hardening exceptions waive the same checks here: its `containerizer.io/waives` label carries
the pod's annotation.
