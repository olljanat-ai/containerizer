    Platform fixes for refactor findings¶

    Containerizer's job is to move as many applications as possible into containers with as few application code changes as possible. Some findings that look like code problems can be satisfied by the platform instead: a pod setting, a volume, a Secret mounted where the runtime already looks. When such a platform technique applies, the finding counts as config (the code stays as it is), the application's rating goes up, and the generated plan.json and Dockerfile header say what was done and why.

    How a technique works¶

    A plan rule in rules/40-plan.yaml names the findings it satisfies with resolves:, and, when the configuration depends on the code, a technique: implemented in containerizer/techniques.py. During the assessment, a finding that a technique resolves gets resolved_by (shown in assessment.json with rule_severity, the rule's own severity) and counts as config. A resolved finding is never sent to a refactoring ("Make it A"). During generation the rule's patch is applied; plan.json lists it in applied, in resolved (rule → findings) and in reasons, and the Dockerfile header carries the reason and references.

    A technique only resolves a finding when the code is within its reach; otherwise the finding stays as it is, so a rating never goes up for code the configuration cannot fix.

    Technique Resolves Generated configuration Stays a finding when
    plan-machine-hostname os-machine-name-switch hostname: in the pod spec, set to the host name the code compares Environment.MachineName with (a production-looking one when there are several; the others are listed in the reason) the comparison is case-sensitive with an upper-case name (== "PRODWEB01"): Kubernetes host names are lower-case
    plan-x509-user-store cert-store an optional Secret <component>-x509-my (External Secrets) mounted read-only at /home/app/.dotnet/corefx/cryptography/x509stores/my, where .NET on Linux reads CurrentUser\My: put each certificate in it as a password-less .pfx key (the name must end in .pfx) the code opens a LocalMachine store other than Root/CA (cert-store-localmachine-code): it does not exist on Linux
    plan-special-folder-workdir os-special-folder-windows a volume at /app/<Folder> for each Path.Combine(GetFolderPath(ProgramFiles), "<Folder>", ...): GetFolderPath returns "" for Windows-only folders on Linux, so the path is relative to the working directory /app the folder is kept in a variable, joined with \, is a file name, or already ships with the app

    LocalMachine\Root and LocalMachine\CA need nothing: on Linux they are the image's CA bundle.

    The three techniques were checked with examples/platform-techniques: the image Containerizer generates for it, run as uid 1654 with a read-only root file system and the generated host name and mounts, takes the production branch, finds the certificate by subject name and reads the vendor file; the same image without them does none of that. Without the techniques the example is rated B, with them A.

    Audit of the refactor rules¶

    Every curated severity: refactor rule, classified (a test keeps this table complete):

    • platform: generated configuration satisfies it; done by a technique above.
    • partial: a platform mechanism exists for some cases or with a trade-off (an unpatched image, a sidecar, one replica); candidates for further techniques.
    • code-only: no configuration reaches it on Linux (the component can still run in a Windows container where the rule says so).

    config rules need no code change by definition; the generator already applies many of them automatically (Kestrel endpoints, connection strings and secret settings from Secrets, Windows paths in configuration, Serilog/NLog sinks, Data Protection keys, writable folders, wkhtmltopdf paths; see Techniques used to avoid application changes), and the others say in their fix what to set.
