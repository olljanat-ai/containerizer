    Secret values in OpenBao¶

    The apps in the appliance's sandbox read their connection strings, secret settings and the settings a release pipeline used to fill (#{Api.Host}#, __Example.Mode__) from the secret store (see External Secrets). On the appliance you enter those values in OpenBao. It runs on the appliance and is served on its normal HTTPS port:

    https://<CZ_HOSTNAME>/ui/. On the admin pages, Secrets ↗ links there.

    You don't have to look up which keys an app needs. Every two minutes the appliance makes one entry for each component that has secrets, with an empty value for each key the component reads. You only type the values.

    Sign in as the administrator¶

    User name admin (method Username). The password is in /etc/containerizer/secrets/openbao-admin (root only, like Grafana's). Change it in OpenBao after the first sign-in. The appliance doesn't need it afterwards.

    The admin user can:

    • read and write every app's values;
    • create users, groups and policies (to give operators access);
    • turn on sign-in methods (for SSO).

    It can't seal OpenBao, change its storage or create a root token.

    Fill in an app's values¶

    1. Secrets engines → apps: one folder per app namespace, one entry per component (apps/<namespace>/<component>, KV version 2, so every save keeps the earlier versions).
    2. Open the entry and choose Create new version. Fill in the values; leave a key empty if the app should keep its own value from appsettings.json. Save.
    3. Within two minutes the appliance:
    4. copies the filled values into the store;
    5. has External Secrets Operator sync the app's Secret right away;
    6. restarts the app's Deployments and StatefulSets that read it, once, and only when what the app gets changed: the pod template's annotation containerizer.io/secrets is a fingerprint of the Secrets it reads (ESO's data hash, never a value). CronJobs pick the values up at their next run.

    The key names are environment variable names: ConnectionStrings__Main sets ConnectionStrings:Main, Api__Url sets Api:Url. They match the Secret store keys in the app's HARDENING.md.

    Files (certificates)¶

    Files an app reads, such as a certificate with its private key (.pfx), are in a second entry of the component: apps/<namespace>/<component>-files. Each key is a file name, its value the file in base64 (for example base64 -w0 app.pfx). Its password, when the app's settings have one (...__CertificatePassword), is a key of the component's own entry.

    • A .pfx or .p12 next to the app's code: the image leaves it out, and the scan mounts it read-only where the app reads it (/app/<path>). Its key starts with the repository's own file (a development certificate); put the environment's certificate in its place.
    • Any other file: turn on Files from the secret store for the app's repository (Admin → Repositories → the repository → Settings) with a folder, /secrets by default. After the next scan each component mounts all of its files there, and its -files entry exists, empty. Add a key per file and point the app's setting at it (/secrets/app.pfx), in settings.yaml or in the settings entry.

    Saving a file restarts the app (a file mounted on its own does not change in a running pod).

    What you see Where it comes from
    An empty key Nobody has filled it yet. The app runs without it (with its appsettings.json value).
    A key with a value you didn't type The app's own development value: the one appsettings.json (or appsettings.Development.json, ...) gives it in the app's repository, where a release pipeline replaces it. The scan leaves these values on the appliance only, never in the output repository, and each key is filled from there once: empty it and it stays empty. Or someone put it in the store by hand before OpenBao was there: it was taken over.
    A key that is not there although HARDENING.md lists it Another part of the appliance fills it (the sandbox identity provider's client secret, lab services' credentials): don't set it.

    Settings that are not secret (a URL with a token in it, say) are in the component's ConfigMap <component>-settings, not in OpenBao: see overview.

    Give operators their own apps (delegated access)¶

    For every app namespace the appliance writes the policy app-<namespace>. It allows reading and changing that namespace's entries (apps/<namespace>/*) and nothing else. An operator who has it sees the names of the other namespaces, never their values.

    Give operators that policy as a user or, better, through a group of your identity provider (next section). With a user (Access → Authentication methods → userpass → Create user, or with the CLI):

    export BAO_ADDR=https://<CZ_HOSTNAME>    # on a workstation; on the appliance just run `bao` (see Recovery)
bao login -method=userpass username=admin
bao write auth/userpass/users/jdoe password='...' token_policies=app-shop,app-hr

    You can write policies of your own, too: one per team over several namespaces, or read-only (["read", "list"]). Don't edit app-*, cz-admin or cz-sync: the appliance rewrites app-* when it differs.

    Sign-in with your identity provider (OIDC / OAuth 2.0)¶

    OpenBao signs people in through any OpenID Connect provider: Microsoft Entra ID, Okta, Keycloak, Google, GitLab, and others. You register OpenBao as an application with the provider. Its groups then decide who gets which policy.

    1. Register an application at the provider

    • Type: web application, authorization code flow (confidential client with a client secret).
    • Redirect URIs:
    • https://<CZ_HOSTNAME>/ui/vault/auth/oidc/oidc/callback (the web UI);
    • http://localhost:8250/oidc/callback (the bao login -method=oidc CLI).
    • A groups claim in the ID token. In Entra ID: Token configuration → Add groups claim → Security groups. The claim then has the groups' object IDs. In Keycloak: a Group Membership mapper with Full group path off.
    • Allow outbound HTTPS to the provider on the appliance's Firewall page (for Entra ID: login.microsoftonline.com).

    2. Turn on the OIDC method in OpenBao (as admin)

    bao auth enable oidc
bao write auth/oidc/config \
  oidc_discovery_url="https://login.microsoftonline.com/<tenant-id>/v2.0" \
  oidc_client_id="<client id>" oidc_client_secret="<client secret>" default_role=people
bao write auth/oidc/role/people \
  user_claim=email groups_claim=groups oidc_scopes=openid,profile,email \
  allowed_redirect_uris="https://<CZ_HOSTNAME>/ui/vault/auth/oidc/oidc/callback" \
  allowed_redirect_uris="http://localhost:8250/oidc/callback" \
  token_ttl=8h token_policies=default

    For Keycloak the discovery URL is https://<keycloak>/realms/<realm>; for Okta https://<org>.okta.com.

    3. Map the provider's groups to policies. One external group per provider group, with an alias that is the group's name or (Entra ID) object ID:

    accessor=$(bao read -field=accessor sys/auth/oidc)
id=$(bao write -field=id identity/group name=shop-operators type=external policies=app-shop)
bao write identity/group-alias name="<group object ID or name>" mount_accessor="$accessor" canonical_id="$id"
# administrators: the admin policy
id=$(bao write -field=id identity/group name=containerizer-admins type=external policies=cz-admin)
bao write identity/group-alias name="<admins group>" mount_accessor="$accessor" canonical_id="$id"

    People now choose OIDC on the sign-in page and get the policies of their groups. Keep the admin user (with a strong password) as the way in when the provider is down.

    Once the method is there, the Secrets ↗ link on the admin pages signs you in to OpenBao with it directly, without OpenBao's sign-in page: it goes to the identity provider (no prompt when you are signed in there already) and comes back to OpenBao's UI signed in. It uses the UI's redirect URI above, so there is nothing more to register. The appliance checks for the method once a minute; until then, or if that sign-in fails, the link opens OpenBao's sign-in page with OIDC selected. To show only OIDC on the sign-in page (the admin user stays under Other):

    bao auth tune -listing-visibility=unauth oidc/

    On an appliance set up before 0.37.0, cz-admin may not tune sign-in methods yet; as admin, add that first: { bao policy read cz-admin; echo 'path "sys/mounts/auth/*" { capabilities = ["read", "update"] }'; } | bao policy write cz-admin -.

    The appliance's own sign-in (Sign-in and roles) is separate: register Containerizer and OpenBao as two applications with the same provider and use the same groups for both.

    How it works¶

    • Service. OpenBao 2.7 runs as the container cz-openbao (systemd containerizer-openbao.service):
    • its own user, a read-only file system, no capabilities;
    • listens on 127.0.0.1:8200 only; Caddy serves /ui/ and its API /v1/ on port 443 with the appliance's certificate;
    • integrated (Raft) storage in /var/lib/containerizer/openbao.
    • Unsealing. OpenBao unseals itself at every start with the static key /etc/containerizer/secrets/openbao-unseal.key, which cz-firstboot makes once. After a reboot nobody has to enter an unseal key. The data can't be read without that file.
    • Setup. cz-sandbox runs python -m containerizer.openbao sync every two minutes, as root. The first run initialises OpenBao:
    • the mount apps (KV version 2), the userpass method with the user admin, the policies cz-admin and cz-sync;
    • a periodic token for the sync, kept in secrets/openbao-sync-token;
    • the recovery key, kept in secrets/openbao-recovery-key;
    • then it revokes the root token. Until then the root token is kept in secrets/openbao-root-token (root only), so a setup that stopped half-way, say during a restart, is finished by the next run.
    • Sync. Each run:
    • reads every component's <component>-secrets ExternalSecret in the sandbox, but only those that read their own namespace's key <namespace>--<component>;
    • adds the missing keys to apps/<namespace>/<component>, empty or with the value already in the store, and never overwrites a value that is there;
    • writes the filled values into the remote Secret containerizer-secrets/<namespace>--<component> with its own field manager (containerizer-openbao), so the keys of the other writers stay, and removes a key emptied in OpenBao;
    • writes the app-<namespace> policies.
    • The sandbox's ExternalSecrets. In the sandbox (clusters/sandbox/flux/apps), each component's <component>-secrets ExternalSecret reads every key its remote Secret has (dataFrom: extract), and its annotation containerizer.io/properties keeps the list. A key that isn't filled is then just not set. With the generated list of properties, External Secrets Operator creates none of a Secret's keys while one is missing. The app folder's own manifests, for the real environment, keep the list.
    • The other values stay where they were. The store is still the namespace containerizer-secrets, and the appliance's own writers fill it there: Git tokens, the Flux webhook, the sandbox identity provider, lab services. Secret files (<component>-files) and keytabs are set as before (External Secrets).

    Forgotten applications¶

    Forget application (Admin → Applications → the application) removes the application's OpenBao entries (apps/<namespace>/..., every version), its policy app-<namespace> and the values copied to the secret store. This happens once the sandbox has removed its namespace (the scan Forget queues does that), within two minutes of it. When the namespace is still there a day later (its repository was enabled and scanned again), the entries stay.

    Appliances set up before 0.41.3 give the sync job the right to delete once: it signs in as admin with the password the appliance generated. If you changed that password, the log of containerizer-sandbox.service says so; run cz openbao-policy as root once (it asks for an OpenBao administrator's user name and password).

    Backup and recovery¶

    Back up /var/lib/containerizer/openbao together with /etc/containerizer/secrets (the unseal key, the recovery key and the sync token): one without the other is of no use. See Backup.

    Recovery. If the sync token is lost (the log of containerizer-sandbox.service then says so), sign in as an administrator (policy cz-admin) and create a new sync token, as root on the appliance:

    BAO_TOKEN=$(bao login -method=userpass -field=token username=admin) \
  bao token create -orphan -policy=cz-sync -no-default-policy -period=768h -field=token \
  > /etc/containerizer/secrets/openbao-sync-token && chmod 0400 /etc/containerizer/secrets/openbao-sync-token

    OpenBao 2.7 refuses bao operator generate-root without a token, so the recovery key alone no longer makes a root token; keep an administrator's password (or an OIDC administrator) at hand.

    On the appliance (as root) the command bao runs the CLI in the OpenBao container and talks to it directly, so leave BAO_ADDR unset there. From your workstation, use your own bao (or vault) with BAO_ADDR=https://<CZ_HOSTNAME>.
