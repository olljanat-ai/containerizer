    Which of your applications can run in containers?¶

    Containerizer scans your whole application portfolio, rates every application from A (container-ready: a modern stack that moves to containers without code changes) to E (not feasible: stays on Windows), explains each obstacle with a fix and references, and generates hardened Dockerfiles and Kubernetes manifests for everything that can move. Then it proves them by building, running and deploying them in its own sandbox cluster.

    Why Containerizer?¶

    • Rules first, AI last

      A data-driven rule set classifies every component, so results are repeatable, explainable and free. An LLM is asked only about what the rules are unsure of, and its answers are validated first.

      How it works

    • Learns by doing

      When unsure, it builds and runs the container, matches failures, patches the plan and retries. Fixes that work become rule proposals that a person approves, so the next run needs no retries.

      Rule review

    • Secure by default

      Chiseled images, non-root, read-only root filesystem, no capabilities, seccomp, Pod Security restricted, and a gate that scans with Trivy and Grype. Every exception is recorded with its reason.

      Security gate

    • Your whole organization

      Schedule scans of Azure DevOps, GitHub and GitLab organizations. New repositories are found automatically, and the A-rated ones are pushed and committed for Argo CD or Flux.

      Organization scans

    • Proven in a sandbox

      A built-in k3s cluster deploys what was generated and reports "deployed and healthy" or exactly why not, even with a restored copy of the application's development database.

      The sandbox cluster

    • A migration plan, not just a verdict

      Every blocker maps to a Linux replacement: System.Drawing to SkiaSharp, WCF to CoreWCF, Windows Service to a worker service, with packages, steps and checks.

      Migration assistant

    • Refactoring patches, verified

      For a B-rated application the LLM makes the targeted code changes, one file at a time. The patch is applied to the assessed commit, checked with the rules, built and run before you download it.

      Refactoring patches

    • Build pipelines for your CI

      GitHub Actions, GitLab CI/CD or Azure Pipelines, for where the code lives: build every component, SBOM and scan it on pull requests, push and sign from the default branch, as a patch to git am.

      Build pipelines

    • Runs in your network

      One immutable appliance with signed upgrades and roll back, only SSH and HTTPS in, and outgoing traffic blocked except for hosts an admin allows. Use Claude, your own self-hosted LLM, or the appliance's built-in CPU LLM when you have no GPU.

      Appliance · The LLM

    • Built for management and audit

      Single sign-on, admins, product owners and operators, an audit log of every change, an access log, trends over time, and SBOMs with licences and CVEs per package.

      Sign-in and roles

    See it in action¶

    Every application, explained¶

    Open an application to see its components, the rating, the main obstacles, and for each finding what to change, why, and where to read more. Everything links back to the rule that decided it.

    How it works

    From blocker to a concrete plan¶

    The migration assistant turns each blocking finding into a Linux-compatible replacement with packages to add and remove, steps and checks. What can't move is marked "keep on Windows" instead of being forced.

    Migration assistant

    Make it A¶

    One order has the LLM fix everything that keeps a B application from A, verifies and repairs the patch, assesses it again and deploys the patched copy to the sandbox beside the original. Every order shows its tokens and time, and needs an administrator's approval until you trust it.

    Refactoring patches

    Watch the portfolio move¶

    Trends show how ratings change over time per business unit and product, so you can see the effect of each fix and each newly learned rule.

    Install the appliance

    Scans that run themselves¶

    Define organization scans on the admin pages, by day and time or on demand. Discover first lists the projects, repositories and latest commits without cloning anything, so deprecated ones can be disabled before the full scan. Every repository shows its last result, and skipped ones are listed with the reason, such as "no source code".

    Organization scans

    A slow LLM never holds up a scan¶

    With a CPU-only or busy LLM, scans can leave the LLM reviews to a queue: uncertain components first, then a second opinion on blockers. Reorder it, limit it to quiet hours or an idle machine, and see how many tokens and hours are left, estimated from the speed it has measured on your LLM.

    The LLM queue

    From finding to a verified patch¶

    For applications that need targeted code changes, an operator orders a refactoring patch. The LLM makes the changes, then Containerizer applies them to the assessed commit, runs the rules again and builds and runs the container. You get a coloured diff, the result per finding and a .patch to apply with git am.

    Refactoring patches

    A person approves what the AI learns¶

    Fixes the learning loop discovers arrive as rule proposals with their evidence. Approve, edit or reject them; approved rules make the next run faster and AI-free.

    Rule review

    Know what's inside every image¶

    CycloneDX SBOMs for each built image, licences checked against your policy, and CVEs per package across the whole portfolio.

    SBOM, licences and CVEs

    Operations you can see¶

    The scan worker exports Prometheus metrics about scans, the process and the VM, with a Grafana dashboard included in the appliance.

    Metrics and Grafana

    Try it¶

    Download the appliance from the latest release, boot it, and point it at your source control.
